## 用户目标

- 在独立软件中集中管理 Clash Verge 已导入的订阅信息，并支持更新节点。
- 将来源订阅的节点加入聚合或从聚合剔除；来源订阅新增、删除后能快速同步聚合。
- 自行创建和调整场景类、策略类代理组，通过拖拽配置节点及候选关系。
- 参考第三方订阅已有的网站分流规则提供场景预设。
- 日常调整无需反复请 Agent 修改大量脚本。

以上记录用户最初意图；具体行为已通过后续访谈收敛，并在完整方案中统一说明。

## 第一轮已确认

用户对 Q1—Q3 回复“全部按你推荐”。

- **Q1：软件职责**。采用独立配置管理器，管理订阅、节点、代理组和规则，应用结果到 Clash Verge；Clash Verge 继续负责代理运行、TUN 和系统代理。
- **Q2：首版使用范围**。面向个人多设备使用，需要考虑配置迁移与同步；具体同步内容和传输方式尚未决定。
- **Q3：编辑与应用**。编辑先保存聚合配置草稿；统一应用时展示变更、校验并生效，失败恢复。订阅节点定时刷新与此关系尚未决定。

## 第二轮已确认

- **Q4：统一管理入口，带生效条件**。用户接受在新软件中统一管理来源订阅的新增、刷新、停用和删除，条件是新软件的调整可以同步到 Clash Verge 并实际生效。首次接入读取已导入订阅；外部修改的识别与冲突处理仍待确认。
  - 现有 `repository.py` 的部署流程已包含配置生成、独立校验、退出客户端、备份写入、重新启动和运行验证，可以支撑聚合配置应用的方向。
  - 这不等于已经实现来源订阅的完整生命周期管理，也不等于所有操作均可无感热更新。具体外部接口、适配方式和版本边界正在核实。
- **Q5：配置权威源**。以新软件保存的可编辑配置为准，支持脱离本代码仓库使用；多设备同步方式另议。现有仓库脚本和旧同步入口不得成为并行覆盖该配置的第二编辑源，见 [ADR 0002](../adr/0002-manager-owned-editable-configuration.md)。
- **Q6：初次迁移**。以现有聚合配置为起点，迁移场景、代理组、候选顺序、节点排除项及专属线路名单，再通过界面调整。动态稳定监测如何迁移、是否推广到其他组，仍待单独确认。

## 第三轮已确认

用户明确选择 Q9 的 B，其他按推荐方案。

- **Q7：多设备共享范围**。共享订阅参与关系、节点筛选、代理组、场景和规则；订阅凭据、本机端口、TUN、当前选择和健康状态由各设备分别保留。同步渠道、触发方式、并发冲突处理尚未决定。
- **Q8：场景与策略复用**。场景负责哪些流量进入对应出口，策略组负责如何选择出口；多个场景可引用同一策略组。支持拖入节点、引用其他组及调整顺序，禁止循环引用。共享策略组变更影响所有引用它的场景；场景也可以独立改选出口。
- **Q9：仅固定成员清单**。只支持用户明确加入的节点成员，来源订阅新增节点全部由用户手动加入，不提供随筛选条件自动扩容的动态集合。筛选与批量选择是否提供作为操作工具，仍可后续讨论，但不能因此让新节点自动入组。该决定固定的是成员关系，不禁止刷新已选节点的连接信息；节点身份、改名和消失的处理仍待决定。
  - 这会改变当前全量 provider 自动接纳新节点的行为。迁移时需将当前候选展开为初始固定成员清单；后续发现的新节点可以显示在来源节点库中，但不能自动进入代理组或聚合候选。
- **Q10：场景预设经审阅更新**。保留现有规则作为起点，参考第三方规则整理带来源和版本的场景预设；更新展示差异，经用户确认后合入，保留自定义内容。

## 第四轮已确认

用户对 Q11—Q14 回复“全部按你推荐的方案来执行”。

- **Q11：节点失效保留标记**。来源节点删除或改名后保留失效标记，展示受影响代理组，由用户重新绑定或移除，不按相似名称自动替换。临时测速超时属于健康状态，不当作节点已删除。
- **Q12：删除前处理引用**。删除来源订阅或代理组前集中展示影响，允许选择替代项或移除依赖；存在空组、无效路由时阻止应用，不级联删除整个场景。
- **Q13：私有 Git 同步脱敏配置**。由软件封装“上传／获取配置”，使用独立保存配置的私有仓库，不要求用户操作代码仓库。获取后进入本机草稿，检查并应用后才影响代理；并发冲突处理尚未确定。见 [ADR 0003](../adr/0003-private-git-configuration-sync.md)。
- **Q14：首版策略范围**。手选、测速优选、按顺序故障转移均可自由创建；动态稳定评估先保留给现有稳定池，首版不推广为任意组的可配置评分系统。

## 第五轮已确认

用户对 Q16 补充多方案与版本覆盖要求，其余按推荐方案。

- **Q15：托盘刷新**。提供手动刷新和托盘定时刷新；刷新来源节点库，新节点只提示待选。已选节点的数据更新无需重启时可自动生效；需要重启或调整成员时提示处理并点击应用。退出管理器后停止其定时任务。
- **Q16：多方案与版本覆盖**。支持保存多套方案，首次只有 `default`；沿用现有 `YYYY.MM.DD.序号` 版本号设计，同一方案由较新版本覆盖较旧版本，不按最后上传时间判断。此要求替代原推荐的同步冲突时逐次选择双方版本；同版本不同内容、未发布草稿、外部 Clash Verge 修改及并发取号的边界仍需确认。见 [ADR 0004](../adr/0004-multiple-versioned-schemes.md)。
- **Q17：规则优先级**。必要直连例外 → 用户自定义规则 → 场景预设 → 剩余基础规则 → 默认出口；专属场景先于宽泛分类，提示重复、冲突和遮挡。提供规则命中预览，用于解释配置，真实连接仍以运行核验为准。
- **Q18：界面结构**。列表和卡片为主，关系图辅助；左侧订阅和节点库，中间场景与策略组，右侧详情，支持搜索、多选、批量拖入及排序，关系图展示引用链。

## 第六轮已确认

用户对 Q19—Q22 回复“全部按你推荐的方案来执行”。

- **Q19：来源库共用**。订阅和节点库全局共用，各方案独立保存参与关系、固定成员、代理组、场景和规则；删除全局订阅时检查所有方案引用。
- **Q20：单个受管聚合入口**。Clash Verge 保留一个受管“订阅聚合”，新软件选择方案并点击应用后切换其内容；仅浏览或编辑其他方案不影响当前运行方案。当前应用的方案由各设备独立记录。
- **Q21：在线发布取号**。离线可编辑和应用，但仅标记本地草稿；上传时读取远端并分配更高的正式方案版本，并发发布重新取号。同版同内容视为一致，同版异内容视为异常并停止同步。历史版本保留，不自动合并不同设备内容；后发布的旧草稿也可能整份替换另一台设备的修改。
- **Q22：外部受管修改**。以软件方案为准，发现 Clash Verge 受管组结构、规则等偏离后提示；用户可导入草稿并发布新版本，否则下次应用恢复软件方案。普通节点手选属于本机状态，不视为配置偏离。

## 当前仓库事实

以下为 2026-10-21 的源代码和文档调查，不代表活动客户端状态。

- 现有聚合策略脚本已支持订阅启停、精确排除节点、专属线路名单、顺序和部分角色；通用代理组拓扑与场景规则仍由 聚合脚本 固定生成。
- 订阅准备工具依靠本机远程订阅卡片的名称读取 URL 和缓存，不自动发现卡片增删。
- 现有同步流程默认复用节点缓存，常规来源订阅刷新交给 Clash Verge；聚合说明中的 provider 独立刷新。因此来源卡片更新不等于聚合立即更新。
- 当前基础分流规则来自历史快照，不随第三方远程规则自动更新。
- 旧同步工具具备设备识别、备份、配置校验、部署、运行验证和恢复能力，但配置来源、版本检查和目标结构与当前仓库策略绑定。
- 已有动态稳定监测面向特定专属线路候选与稳定池，不能直接视为任意策略组的通用能力。
- 现有版本格式为 `YYYY.MM.DD.序号`，按数字段比较，版本发布要求严格递增，来源内容通过指纹核验；同版本不同指纹会报错。当前清单只有一份，版本由维护者传入，未实现多方案或跨设备并发取号；Git 分叉直接停止。参见 版本实现和版本维护。

## Clash Verge 集成核实

- 仓库现有 `repository.py` 的 `deploy` 流程已实现生成、预检、正常退出、备份写入、启动、运行核验与选择/监测恢复；仅配置完全相同的路径可跳过重启。因此最低可行的聚合应用路径已经存在，但完整来源订阅管理仍需开发。
- [Clash Verge 官方 URL Scheme 文档](https://www.clashverge.dev/guide/url_schemes.html)公开了导入订阅的能力。在此次核实的公开能力中，未发现供独立程序直接调用的完整来源订阅管理 API。
- 官方 [profile.rs](https://github.com/clash-verge-rev/clash-verge-rev/blob/main/src-tauri/src/cmd/profile.rs) 中的导入、创建、更新和删除操作是 Tauri 命令，[官方前端](https://github.com/clash-verge-rev/clash-verge-rev/blob/main/src/services/cmds.ts)使用 `invoke` 调用，不能直接视为外部 HTTP API。
- [Mihomo API](https://wiki.metacubex.one/api/) 的 provider 更新针对已加载节点集合，不等于刷新 Clash Verge 来源订阅卡片。
- 以上为 2026-10-21 的接口与源码调查，未对本机活动客户端进行操作或验证。文件适配、客户端版本支持范围及尽量减少重启的方式仍需设计。

## 当前设计树与工程收敛

独立发行的实现调查已确认：现有 `repository.py` 依赖仓库目录与版本清单，`prepare.py` 调用外部 Node，`device.py` 调用 PowerShell 7 和仓库脚本；必须解耦才能脱离代码仓库运行，不能把现有后端原样打包后视为完成。

原先打包 Python 后端的建议已由用户接受的新选择替代：Electron + React + TypeScript/Node.js 核心，业务模型、校验、配置生成、版本同步、部署事务与稳定池评估迁移到 TypeScript，正式发行包不携带 Python。

选型依据与迁移约束：

- 检查 `prepare.py`、`sync.py`、`config_version.py` 和 `stability.py` 的核心路径后，主要依赖 YAML、JSON、文件、哈希、HTTP、子进程、统计和计时，没有发现必须保留 Python 的专属能力。现有 JavaScript 生成逻辑也能作为迁移基础，但固定拓扑需改为通用模型。
- [Electron 主进程使用 Node.js](https://www.electronjs.org/docs/latest/tutorial/process-model)，可以承载本机逻辑；[utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process)可隔离 Node 工作进程。因此移除 Python 不等于把所有任务放进界面线程，也不需要因此引入独立网络后端。
- 领域规则模块保持不依赖 Electron 和 Windows；Clash Verge 文件结构、Mihomo 通信、Git 与 Windows 本机操作集中在对应模块。Windows 专有功能仍可能需要受控原生辅助程序，不能把“核心 TypeScript”误称为所有系统功能均由纯 JavaScript 实现。
- 迁移需通过界面无关的行为契约验收：备份一致性、互斥、异常与崩溃恢复、设备字段保留、手选恢复、并发发布、失效成员和稳定池评估。无需原样保留旧实现中的仓库路径或固定代理组结构。
- 稳定池监测也需迁移，不能以隐藏 Python 任务的方式维持正式运行依赖。工作进程隔离不等于退出后仍运行的系统服务；既有监测的后台运行、停止与恢复语义需在整体方案中明确并验收。
- Electron 的包体和常驻开销仍然存在；移除 Python 主要减少跨语言模型、运行环境和发行维护工作。私有 Git 同步可评估随包交付 [MinGit](https://gitforwindows.org/mingit.html)，其他本机依赖需逐项明确打包或替换方式。

- 产品定位：独立管理器，首版个人多台 Windows，长期考虑产品化；代理运行由 Clash Verge 承担。
- 来源与成员：全局来源库、方案固定成员、失效保留标记、删除先处理依赖、刷新不自动扩容。
- 多方案与同步：初始 `default`、单聚合入口、在线取号、同方案较新版本覆盖、历史保留与异常摘要检测。
- 组与场景：复用策略、禁止循环、常规策略自由创建、现有稳定池迁移、场景预设审阅合入。
- 使用与交付：草稿后应用、列表卡片拖拽、TypeScript 核心、便携包和手动升级。
- 工程细化：完整方案已补齐本机绑定、停用与删除、刷新基线、DIRECT/REJECT、受控 provider、并发发布、后台生命周期、应用恢复和验收标准。

用户随后要求重新核对方案，若无待决定问题就提交并推送。复核补充及最终工程契约以完整方案第 12 节为准；本轮只归档设计，后续按明确的软件开发指令实施。
