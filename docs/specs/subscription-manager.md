# 独立订阅配置管理器

> 状态：本地规格草稿。内容依据已确认访谈和复核方案整理；项目 tracker／triage 配置及测试接口核对完成后发布，并应用 `ready-for-agent` 标签。

## Problem Statement

用户已经在 Clash Verge 中导入多份来源订阅，并通过仓库脚本维护聚合订阅、场景分流、专属线路候选与选路策略。日常新增或退订、排除节点、调整代理组及网站出口，仍需修改策略文件或较长的脚本，再生成、备份和部署；来源订阅刷新也不等于聚合立即加载相同节点信息。

用户希望自己通过独立软件完成这些操作，减少对 Agent 修改脚本的依赖。软件需要支持多方案、多台设备及可靠恢复，并为后续长期维护和向其他用户开放保留清晰的产品结构。配置编辑、正式发布、本机应用和节点健康必须明确区分，避免出现界面保存成功却尚未生效、来源刷新悄悄扩充候选、或不同工具互相覆盖配置的问题。

## Solution

提供采用 Electron、React 和 TypeScript/Node.js 核心的独立 Windows x64 配置管理器，正式发行不依赖 Python 或代码仓库。Clash Verge 继续负责代理运行、TUN 和系统代理。

软件统一展示来源订阅和节点库，首次将现有聚合迁移为 `default` 方案。用户可以新建或复制方案，在列表和卡片界面中搜索、多选、拖入节点、引用策略组、调整候选顺序、创建场景以及维护网站规则。节点采用固定成员清单，来源新增节点只提示待选；场景预设记录来源和版本，经审阅后合入。

编辑先保存聚合配置草稿。明确应用时执行依赖校验、差异预览、内核预检、备份、受管更新、运行核验和状态恢复；遇到缺少正常退出接口的客户端版本，提示用户手动退出后继续。只有全部必要步骤成功才确认已应用。

软件封装私有 Git 配置同步。各方案独立使用 `YYYY.MM.DD.序号`，在线发布时自动分配更高版本；同方案较新正式版本覆盖较旧内容，历史保留，不自动合并不同设备的修改。发布、获取和应用分别操作，凭据、端口、TUN、当前选择与健康状态留在各设备。

## User Stories

### 接入与来源订阅

1. 作为首次使用者，我希望软件发现并校验本机 Clash Verge 和配置目录，以便快速建立有效连接。
2. 作为首次使用者，我希望发现多个有效客户端或配置目录时能明确选择，以便避免管理错误的设备配置。
3. 作为配置管理器用户，我希望未知客户端版本或索引结构仅进入只读状态，以便了解限制并保留现有配置。
4. 作为已有订阅的用户，我希望读取 Clash Verge 已导入的来源订阅，以便无需逐个重新录入。
5. 作为已有聚合配置的用户，我希望首次迁移产生 `default` 方案并保留现有场景、组、名单、规则和顺序，以便接着当前配置使用。
6. 作为配置管理器用户，我希望在软件内新增来源订阅并预览获取的节点，以便集中管理订阅入口。
7. 作为配置管理器用户，我希望手动刷新来源订阅，以便及时获取供应商更新。
8. 作为配置管理器用户，我希望继承并调整订阅刷新周期，以便控制自动获取的频率。
9. 作为配置管理器用户，我希望窗口关闭到托盘后仍能执行已启用刷新，以便保持来源节点库更新。
10. 作为配置管理器用户，我希望看到“已获取”“待应用”和“已生效”的区别，以便知道变化是否已进入运行配置。
11. 作为配置管理器用户，我希望查看来源提供的流量、到期和刷新信息，以便了解订阅状态。
12. 作为配置管理器用户，我希望来源未提供元信息时显示未知，获取失败时标记旧值，以便避免将缺失数据误认为零或最新数据。
13. 作为配置管理器用户，我希望来源获取失败时保留最后有效快照，以便继续查看和处理现有配置。
14. 作为配置管理器用户，我希望原来源卡片更新与聚合节点生效分别展示，以便不会误认为两个动作已经同步完成。
15. 作为已有多个 profile 的用户，我希望接管聚合时保留其他 profile、全局扩展和设备设置，以便继续使用既有配置。

### 节点库与固定成员

16. 作为多方案用户，我希望所有方案共用来源订阅和节点库，以便不必重复登记相同订阅。
17. 作为需要管理大量节点的用户，我希望搜索、筛选和多选节点，以便快速找到当前要加入的成员。
18. 作为配置管理器用户，我希望批量拖入时保存当时明确选择的节点，以便候选范围始终可控。
19. 作为配置管理器用户，我希望将节点拖入组时明确加入对应方案的聚合成员，以便成员和组引用保持一致。
20. 作为配置管理器用户，我希望来源新增节点只出现在待选库，以便由自己决定是否加入聚合和代理组。
21. 作为配置管理器用户，我希望节点排除项刷新后仍然有效，以便不会反复出现已剔除候选。
22. 作为配置管理器用户，我希望已选节点的连接数据能够刷新而不改变固定成员关系，以便保留编组并接收供应商更新。
23. 作为配置管理器用户，我希望节点删除或改名后保留失效引用并展示影响，以便决定重新绑定还是移除。
24. 作为配置管理器用户，我希望测速超时只影响健康状态，以便真实节点不会被当作已删除成员。
25. 作为配置管理器用户，我希望同一来源重名节点被标记为歧义，以便不会自动绑定到错误候选。
26. 作为配置管理器用户，我希望系统不根据相似名称自动寻找替代节点，以便避免住宅属性或地区要求被悄悄改变。
27. 作为配置管理器用户，我希望移出聚合成员前看到所有组引用，以便一次完成必要调整。
28. 作为多方案用户，我希望在某方案停用来源时不影响其他方案，以便维护不同用途的配置。
29. 作为配置管理器用户，我希望全局删除来源前查看所有方案依赖，以便避免留下无效组或规则。
30. 作为多设备用户，我希望本机解绑来源不会被当作全局删除，以便其他电脑仍能使用相同来源。

### 方案与本机状态

31. 作为首次使用者，我希望方案库初始只有 `default`，以便从清晰的起点开始。
32. 作为多方案用户，我希望新建和复制方案，以便分别配置日常、办公等用途。
33. 作为多方案用户，我希望修改方案、组和场景显示名称后引用仍然有效，以便自由整理界面。
34. 作为配置管理器用户，我希望草稿自动保存并具有本机恢复快照，以便减少未发布编辑丢失。
35. 作为多方案用户，我希望浏览和编辑其他方案不影响当前运行，以便完成整次调整后再切换。
36. 作为多方案用户，我希望明确应用所选方案后才改变代理配置，以便控制生效时机。
37. 作为多方案用户，我希望 Clash Verge 只保留一个受管聚合入口，以便统一从新软件切换方案。
38. 作为多设备用户，我希望每台电脑独立记录已应用方案和当前选择，以便不同设备可以使用不同出口。
39. 作为离线用户，我希望能够编辑并应用合法的本地草稿，以便没有 Git 网络连接时也能管理代理。
40. 作为配置管理器用户，我希望区分已发布版本、本地草稿和实际已应用内容，以便准确理解当前状态。
41. 作为多方案用户，我希望删除当前生效方案前先选择并应用有效替代方案，以便不会留下不明确的运行配置。
42. 作为需要恢复配置的用户，我希望将历史方案恢复为草稿并发布更高版本，以便回退设计同时保留版本历史。

## Implementation Decisions

- 产品采用独立配置管理器定位，首版为 Windows x64；代理内核、TUN 与系统代理继续由 Clash Verge 管理。便携发行、手动升级、用户配置与程序分离。
- 桌面界面采用 Electron 和 React，领域规则、方案校验、配置编译、版本同步、事务编排及稳定池评估使用 TypeScript/Node.js。正式运行不依赖 Python；旧实现仅作为开发期行为参照。
- 领域核心保持独立于 Electron 和 Windows。将本机来源适配、方案存储、共享发布、应用事务、后台执行与 Windows 操作集中成职责清晰的模块；必要辅助程序随包交付。
- React 通过受限应用命令访问核心，界面与测试使用相同的可观察业务接口。接口覆盖读取状态、保存方案、预览、应用、恢复、刷新、发布和获取等用户动作，隐藏内部阶段与系统适配细节。
- 以稳定标识引用来源、方案、组和场景，名称仅用于展示。节点以稳定来源标识和原始名称对应；同源重名不自动合并，改名按失效引用处理。
- 来源目录与节点库全局共用。每套方案保存自己的来源参与关系、固定聚合成员、组、场景、规则和默认项；组的节点引用必须属于该方案聚合成员。
- 所有方案初始只有 `default`。Clash Verge 仅保留一个受管聚合入口，当前应用方案与当前编辑方案分别记录，草稿可离线编辑及应用。
- 共享设计采用带格式版本的 JSON，使用稳定序列化生成内容摘要，保留具有业务含义的数组顺序。软件版本、文件格式版本、方案版本、来源快照与本机应用记录分别演进。
- 订阅 URL、节点凭据、原始响应、私有暂存及备份只保存在本机 Clash Verge 管理目录。共享发布仅接受字段白名单；设备字段、选择和健康状态不参与方案版本。
- 首次识别校验客户端身份、目录结构、索引与版本兼容；未知写入格式只读。迁移保留现有组名、场景、规则、专属线路限制、排除项及有效默认选择，旧全量候选展开为当时的固定成员。
- 接管为显式事务：保留聚合入口身份，切换到新软件的专属扩展绑定，并保留可恢复的旧扩展与旧记录。必须验证受支持旧工具在记录存在和回退识别两条路径均拒绝覆盖；单一归属标记不足以证明保护有效。
- 新旧工具的部署与导入互斥协议需要兼容；明确反向交还流程。归属转换、锁和扩展绑定不得依靠用户避免误开旧工具来维持正确性。
- 节点搜索与筛选仅用于当前选择，批量拖入不保存自动扩容条件。来源新增节点不进入运行聚合，节点缺失或改名保留待处理引用，临时测速失败只影响健康状态。
- 来源刷新继承已有周期，缺少有效周期时采用两小时基线并允许修改；窗口到托盘继续运行，显式退出管理器停止其刷新任务。
- 来源快照获取、原卡片落盘及内核 provider 生效分别处理。受控本地 provider 仅包含明确固定成员；热刷新须在目标内核验证后开启，并与应用共用写互斥、重新校验生效方案与快照基线。
- 原卡片可能继续由 Clash Verge 更新；软件只读吸收经校验的缓存，不与客户端并发修改其索引、绑定或原卡片。缺少安全在线写入方式时，变更留待正常退出后的事务。
- 元信息记录来源和时点，缺失显示未知，失败保留旧值并标记陈旧。热刷新更新本机数据记录，不改变方案版本或被误判为受管结构偏离。
- 支持手选、测速优选与顺序故障转移组，允许组引用和顺序调整并禁止循环。DIRECT 与 REJECT 只能显式加入，不作为异常或空组的自动替代。
- 初始场景采用现有八类设计。第三方预设只解析支持的规则数据，记录来源和版本，不执行第三方脚本；更新审阅后合入，保留用户覆盖。不支持内容影响既有分流时阻止迁移成功。
- 规则优先级为必要直连例外、自定义规则、场景预设、剩余基础规则和默认出口；专属服务先于宽泛分类。合法跨层覆盖确定胜出项并解释，同层未解决冲突阻止应用，命中预览不推断缺失的网络上下文。
- 删除方案、组、来源或聚合成员先计算引用影响；初始 `default` 方案不可删除，其他方案再按生效状态处理；空组及无效路由必须修复。方案内停用、本机解绑和共享来源全局删除分别表达；全局删除发布前读取并校验远端完整引用。
- 每套方案独立使用 `YYYY.MM.DD.序号` 并按数字段排序，在线发布时基于最新远端分配更高版本。发布日期不得低于该方案已有正式日期，时钟回拨不破坏单调性。
- 同一方案按较新正式版本整份覆盖，不合并不同设备内容。后发布的旧草稿可能替换此前修改；历史保留，同版同摘要为一致，同版异摘要或历史被改写则停止同步。
- 发布基于最新远端提交构建本次变更，保留其他方案和来源；条件推送失败有界重读、取号及重试，不强推。发布请求标识在重试间稳定，结果不确定时先核对远端历史，已成功请求不再次发版。
- 全局来源目录独立修订，与受影响方案在同一发布事务内变更；按明确增改删操作更新最新远端状态，不用旧目录整份覆盖。来源和方案删除保留记录，旧草稿不能静默复活对象。
- 获取较新正式内容前保存未发布草稿的本机恢复快照；获取与发布不自动应用。缺少本机来源仍可保存方案，应用前必须补齐所用来源及成员。
- 私有 Git 只传配置数据，不执行其内容。首次需要用户配置已有私有仓库并认证，必要工具随包交付；零开发环境不代表无需账号配置。
- 应用事务统一负责预览、依赖检查、私有生成、目标内核预检、设备互斥、恢复和成功凭证。修改已有内容前备份并校验，最小更新受管内容，保留无关订阅与设备字段。
- 在暂停监测等首个副作用之前持久保存原客户端、profile、有效选择、文件与绑定基线，以及监测存在、运行、启用和归属状态。各阶段记录意图与完成结果，崩溃恢复按实际状态幂等补偿。
- 缺少正常退出接口时等待用户手动退出，不将隐藏窗口、强杀或模拟托盘点击当作正常退出。退出后重读最终磁盘状态，再核对并备份。
- 写配置前失败只补偿本次改变的进程与监测状态；写配置后使用校验备份恢复。取消、退出失败、备份失败和崩溃都须覆盖；后续修改保护阻止恢复覆盖用户新工作。
- 实际核验覆盖 provider、组类型、候选范围与顺序、规则、聚合入口及有效选择。有效手选按稳定身份迁移，监测按原状态恢复并重新评估动态优先值，不盲目回写旧动态选择。
- 所有必要核验与恢复完成后才确认成功；相同内容且运行验证通过可跳过重启。恢复失败保留明确状态和备份位置，未完成恢复阻止新写入事务。
- 独立稳定监测迁移到相同 TypeScript 实现的无界面后台模式，保留已有登录任务语义、独占控制和停止清理；只调整既有目标稳定池。新设备不擅自启用，切换到不含目标池的方案时正常停止。
- 便携目录移动和软件升级检查后台任务归属及程序版本；界面退出与独立监测分别管理，应用事务需先完成或安全恢复后才能退出。

## Testing Decisions

- 主要测试接口是供界面调用的应用命令及其可观察结果，围绕“用户提交方案或操作意图后，得到什么状态、持久内容及运行结果”编写测试。采用一个主要业务测试入口，进程通信和桌面外壳只做必要适配验收，不为每个按钮建立独立业务实现。
- 沿用已讨论的应用事务、共享发布和稳定池行为契约；现有代码尚无统一桌面命令入口，TypeScript 迁移时整合这些契约。通过实际及测试适配提供文件、时钟、控制器和远端环境，故障注入不依赖访问私有函数或锁定调用次数。
- 好的测试验证外部行为、业务不变量和失败后的实际状态，而不是函数拆分、内部阶段命名、界面组件树或实现顺序快照。测试数据脱敏，明确区分既有行为迁移和新需求改变。
- 方案与编译验收覆盖固定成员、节点重名和改名、组引用与循环、依赖删除、显式内置目标、候选顺序、场景限制以及确定性内容摘要。来源刷新和设备状态不应制造正式版本。
- 规则验收复用现有聚合脚本的首条匹配测试思路，覆盖根域、子域、专属服务先于宽泛分类、合法自定义覆盖、同层冲突和上下文不足；不能只断言某条规则存在。
- 迁移使用脱敏旧输入与旧实现结果作对照，比较成员、引用、规则首条命中、默认项和稳定池决策。固定名单取代旧全量自动扩容是已确认的新行为，不能机械要求与旧行为完全相同。
- 文件事务复用现有同步器的临时设备和故障注入先例，覆盖备份失败、部分写入失败、启动失败、运行核验失败、后续修改保护、无关 profile 与设备字段保留以及相同配置不重启。
- 额外注入暂停监测后取消、退出超时、备份前后崩溃和恢复中断；断言原运行状态得到补偿或明确报告恢复失败。没有配置写入时不能尝试使用不存在的文件备份，未完成事务不能产生成功凭证。
- 接管验收实际执行受支持旧入口的识别和部署路径，覆盖记录存在、回退识别、并发锁和显式反向交还；证明它不会重写新软件已接管的运行配置，而不只检查归属字段存在。
- 刷新验收使用可控来源响应，覆盖新节点只待选、删除与改名保留失效项、健康失败不改成员、错误快照不覆盖有效缓存、元信息缺失和陈旧状态，以及原卡片和运行 provider 的独立状态。
- 对目标 Mihomo 执行隔离配置与 provider 刷新验收，检查热刷新与方案切换竞争、失败恢复、候选范围和实际运行记录。隔离环境关闭 TUN、使用回环控制器，不借用活动内核验证写入。
- Git 验收复用临时远端及两台临时设备先例，覆盖离线编辑、较新覆盖、并发取号、同版异内容、时钟回拨、未知格式、历史篡改、未发布草稿恢复以及其他方案保持完整。
- 发布幂等验收模拟远端已接收但客户端未收到结果，重试必须识别既有请求，不能重复取号或覆盖其后其他设备版本。目录与方案原子变更、删除记录及旧草稿重发须共同校验。
- 稳定池验收复用现有确定性样本、时钟和决策结果，覆盖评分、冷却、连续确认、劣化恢复、样本去重及停止清理；断言只调整目标稳定池，不影响费用池、模式和规则。
- 界面与发行验收覆盖多选拖入、排序、共享引用影响、差异预览、状态区分、无效编辑阻止，以及干净 Windows x64 环境中的便携运行、升级保留配置和后台任务重新绑定。
- 开发测试不自动操作用户电脑界面；真实首次接管、托盘退出、激活和网站体验由用户操作，再用允许的命令行和控制器读取得到证据。配置已加载、HTTP 探测及账号可用分别报告。

## Out of Scope

- 替代 Clash Verge 成为完整代理客户端，或自行接管代理内核、TUN 和系统代理。
- 首版支持 Windows x64 以外的系统或架构。
- 根据来源、地区或筛选条件自动把新增节点纳入聚合；自动替换改名或消失的节点；异常时自动补入 DIRECT 或其他出口。
- 将动态稳定评估推广为任意代理组的通用可编程评分系统。
- 执行第三方订阅脚本、无审阅跟随第三方规则更新，或静默覆盖用户自定义内容。
- 自动逐字段合并两台设备对同一方案的改动；方案新旧关系遵循已选择的正式版本整份覆盖。
- 同步真实订阅凭据、端口、TUN、当前选择、健康状态、私有快照和部署备份。
- 通过配置 Git 仓库同步或执行软件程序，首版内置自动升级和安装器。
- 本次规格直接承诺云端账号、团队协作服务或正式公开发行；长期产品方向保留，首版先完成个人多设备闭环。
- 以配置校验或基础 HTTP 探测保证全部网站、账号、出口属性、吞吐或长期网络质量。

## Further Notes

- 本规格综合 24 项已确认选择及其复核补充，采用项目领域词汇，并延续独立管理器、软件配置权威源、私有 Git、多方案版本和 TypeScript 核心五项架构决策。
- 本规格由设计访谈与复核方案整理；现有同步工具不能被视为已经实现本规格。
- 实施顺序为领域核心与兼容探针、应用事务与接管、可视化编辑、刷新及稳定监测迁移、Git 同步和便携发行。阶段用于组织实施，首版完成需覆盖整个用户闭环。
- 生产集成必须明确支持的客户端、内核及数据格式版本。来源卡片管理与内核 provider 刷新是不同能力，热更新须经实测，不承诺所有修改均无感生效。
- 覆盖历史内容不删除历史记录。用户选择的发布规则允许后发布旧草稿生成更高版本并替换他人修改，系统解释结果并保留追溯，不自行改成自动合并策略。
- 本文件作为本次已授权实施的规格依据；当前未发布到 tracker。实现入口为本仓库根目录，验证范围与真实设备待验收事项见使用说明，不能把构建和隔离测试当作真实部署。
